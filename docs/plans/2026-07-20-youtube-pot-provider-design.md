# YouTube PO Token provider design

Comandita will keep downloading only public YouTube URLs and will not use Google accounts, cookies, or private content. A separate internal PO Token provider will generate short-lived attestation tokens required by YouTube for some public playback requests. The bot will call that provider only through a ClusterIP Service in the `comanditabot` namespace; no Ingress or externally reachable port will be created.

The application repository will contain a new `youtube-pot-provider/` directory with a Dockerfile pinned to version `1.3.1` of the upstream BgUtils provider. The existing build workflow will build and push both images from the same source SHA: `apps/comanditabot` and `apps/comanditabot-youtube-pot-provider`. This makes each GitOps deployment auditable and ensures the plugin and provider images move together.

The bot image will install the matching `bgutil-ytdlp-pot-provider` and `yt-dlp-ejs` Python packages, plus Node.js 22 to resolve YouTube's JavaScript `n` challenge. When `YOUTUBE_POT_PROVIDER_URL` is configured, its yt-dlp options will select the `mweb` YouTube client, enable Node, and direct the plugin to the internal Service URL. Other platforms and a bot without that environment variable retain existing options. Provider failures remain normal `DownloadError` failures and are logged without URLs containing query parameters.

The Helm chart will add a one-replica provider Deployment and ClusterIP Service. It will use fixed resources, a non-root runtime, dropped capabilities, runtime-default seccomp, a read-only root filesystem, and a writable `emptyDir` only if the upstream process needs temporary storage. Tests will verify the yt-dlp options and render the complete chart; an end-to-end metadata request from the deployed bot pod will verify that the provider is visible and used.
